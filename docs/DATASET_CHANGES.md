# 데이터셋 추가: DLA7 2018-08-03 배정 실험용

이전 실험의 데이터(경로 24개, 방문 순서 실험용, 지금은 `v1/data/`)는 그대로 두고, 차량 배정 실험용 데이터를 `data/station_day/`에 새로 추가했다. 이전 실험의 코드(`v1/` 아래 `data_fetch.py`, `solvers.py`, `run.py`, `check.py`)의 동작은 바꾸지 않았다. 아래의 경로와 명령은 저장소 폴더 기준이다.

| 파일 | 내용 |
|---|---|
| `data/station_day/station_day.json` | 거점, 기준 시각, 차량 6대, 배송지 923곳, 원래 배정과 기록된 방문 순서 |
| `data/station_day/travel.json` | 경로별 원자료 이동시간 행렬(새 ID 기준) |
| `data/station_day/manifest.json` | 출처, 선택 규칙, 추정식 계수와 오차, 파일 해시 |
| `data_fetch_station.py` | 원자료에서 위 세 파일을 만드는 스크립트. `v1/data_fetch.py`의 함수 두 개를 가져다 쓴다 |
| `dataset.py` | 데이터를 읽고 이동시간을 조회하는 모듈 |

## 왜 바꿨는지

기존 데이터는 한 차량에 이미 배정된 배송지의 방문 순서만 다룬다. 서로 다른 스테이션·날짜의 경로 24개라 배송지를 차량 사이에서 옮길 수 없다. 어느 차에 어느 배송지를 실을지부터 다루려면 같은 스테이션에서 같은 날 출발한 인접 경로들과, 지금까지 지우던 좌표·용량·부피가 필요하다.

## 무엇을 골랐는지

- 스테이션 DLA7, 2018-08-03. 공식 학습 자료에 이 날 경로가 56개 있고, 그중 6개를 골랐다.
- 규모: 차량 6대, 배송지 923곳(경로당 137~173곳), 물품 1,426개, 마감이 있는 물품 166개(배송지 94곳).
- 선택 규칙: 두 경로의 배송지가 500m 안에 있으면 연결된 것으로 보고, 연결된 6~8대 묶음 가운데 "묶음 안 다른 경로의 배송지가 500m 안에 있는 배송지 비율"이 가장 높은 묶음을 골랐다. 묶음 크기별 최고 비율은 6대 52.3%, 7대 50.4%, 8대 50.6%여서 6대 묶음이 선택됐다.
- 경로별로 보면 이 비율은 37.1%~71.1%이다.
- 차량 용량은 6대 모두 3,313,071cm³이고 `route_score`는 모두 Medium이다. 원래 배정의 적재율은 60.4%~80.6%이다.

고른 경로 ID는 `manifest.json`의 `selection.route_ids`에 있다.

## 이전 실험 데이터(v1/data/)와 다른 점

**추가된 필드**

- 거점 좌표(`depot`). 6개 경로의 스테이션 좌표가 같아서 거점은 하나다.
- 차량별 용량(`capacity_cm3`), 출발 오프셋(`departure_offset_seconds`), `route_score`.
- 배송지별 위도·경도, 구역 ID(`zone_id`), 물품 부피 합(`volume_cm3`), 원래 경로(`route_id`), 원래 ID(`raw_id`).
- 구역 ID가 원자료에 없는 배송지 2곳은 `null`이다.
- 부피는 물품별 `depth × height × width`(cm³)를 배송지 단위로 더한 값이다. 물품 하나하나의 치수는 저장하지 않았다.

**시간 기준**

- 기존: 경로마다 자기 출발 시각이 0초.
- 신규: 고른 경로 중 가장 이른 출발 시각 2018-08-03 16:26:20 UTC가 0초다. 모든 시간대(`windows`)가 이 기준의 초 단위다.
- 차량별 출발 오프셋은 0, 5, 6, 340, 636, 730초다. 차량의 시계는 0이 아니라 자기 오프셋에서 시작해야 한다.
- 시간대 시작이 음수인 물품이 있다(기준 시각 전에 이미 열린 시간대). 마감 범위는 12,820~52,360초다.
- `windows`의 형식은 기존과 같은 `[시작, 마감, 서비스시간]`이고 시간대가 없으면 시작·마감이 `null`이다.

**배송지 ID 규칙**

- 원자료의 배송지 ID(`AD`, `AF` 등)는 경로 안에서만 유일하다. 새 ID는 `경로ID:원래ID`다. 예: `RouteID_599f5d4b-9066-41e8-82b5-f3791d13205c:AE`.
- 스테이션은 원자료에서 경로마다 ID가 다르지만 모두 `DEPOT`으로 바꿨다. 원래 ID는 차량의 `raw_station_id`에 있다.

**이동시간 저장 방식**

- 기존: 경로별 `travel[출발][도착]` 사전.
- 신규: `travel.json`에 경로별로 `nodes`(첫 칸이 `DEPOT`, 이어서 배송지 ID)와 `seconds`(같은 순서의 2차원 배열)를 저장했다. 923곳 전체의 행렬은 만들지 않았다.

**기준선**

- 차량의 `recorded_order`가 원래 배정이자 기사가 실제로 방문한 순서다(거점 제외).

## 경로 간 이동시간 추정 방식과 오차

원자료의 이동시간은 같은 경로 안의 지점끼리만 있다. 서로 다른 경로의 배송지 사이는 좌표 거리로 추정한다.

- 식: `초 = a × km^b`. km는 위도·경도의 대원 거리다.
- 맞춘 자료: 고른 6개 경로의 경로 내부 배송지 쌍(방향 구분) 141,956개. 시간이 0인 16쌍은 로그를 쓸 수 없어 제외했다.
- 방법: 로그-로그 최소제곱.
- 계수: **a = 272.52, b = 0.6783**.

오차는 경로 하나를 빼고 나머지 5개로 맞춘 뒤 뺀 경로로 잰 값이다(6번 반복해 합침).

| 거리대 | 쌍 수 | 실제 평균(초) | 평균 절대오차(초) | 중앙 오차율 | 치우침(초) |
|---|---:|---:|---:|---:|---:|
| 전체 | 141,972 | 323.3 | 51.8 | 13.8% | −6.6 |
| 0~0.25km | 6,698 | 99.0 | 48.1 | 43.3% | −20.7 |
| 0.25~1km | 49,756 | 213.6 | 51.9 | 20.6% | −13.0 |
| 1~3km | 82,190 | 395.2 | 52.0 | 10.7% | −1.1 |
| 3km 이상 | 3,328 | 641.5 | 51.9 | 6.3% | −20.7 |

치우침이 음수면 추정값이 실제보다 짧다는 뜻이다. 6개 경로 전부로 맞췄을 때의 오차(평균 절대오차 50.8초, 중앙 오차율 13.5%)도 `manifest.json`에 있다.

**거점 구간**은 따로 맞췄다. 거점→배송지는 a = 227.59, b = 0.8082(중앙 오차율 2.7%), 배송지→거점은 a = 260.16, b = 0.7607(중앙 오차율 2.9%)이다. 다만 거점은 6개 경로가 공유하므로 모든 배송지의 거점 구간이 원자료 행렬에 이미 있다. 그래서 `dataset.py`는 거점 구간에 추정값이 아니라 원자료 값을 돌려준다. 거점 추정식은 참고용으로만 기록했다.

**조회 함수**

```python
from dataset import StationDay
day = StationDay()
seconds, estimated = day.travel(origin_id, destination_id)
```

- 두 지점이 같은 원래 경로에 속하거나 한쪽이 `DEPOT`이면 원자료 값과 `estimated=False`를 돌려준다.
- 서로 다른 경로의 배송지 쌍이면 추정값과 `estimated=True`를 돌려준다.

## 검증한 것

- 배송지 923곳, 물품 1,426개가 원자료와 일치한다.
- 모든 배송지의 좌표·구역, 모든 물품의 시간대·서비스시간, 배송지별 부피 합이 원자료와 일치한다.
- 물품 3개의 시간대를 원자료 UTC 값에서 직접 계산해 저장값과 대조했다(예: 16:00:00 ~ 다음 날 00:00:00 → −1,580 ~ 27,220초).
- 원래 배정에서 6대 모두 부피 합이 용량 이하다.
- 조회 함수가 같은 경로 쌍 144,747개(거점 포함)에서 원자료 값과 똑같이 나온다.
- 크기가 0 이하인 물품은 이 표본에 없다.
- 선택 규칙을 별도 구현으로 다시 계산해 같은 6대 묶음이 나오는 것을 확인했다.

`python dataset.py`를 실행하면 원자료 없이 확인할 수 있는 항목(파일 해시, 개수, 용량, 같은 경로 쌍 조회)을 다시 검사한다.

## 알려진 한계

- **경로 간 이동시간은 추정값이다.** 실제 값이 없어서 경로 간 쌍의 오차는 잴 수 없었다. 위 오차는 경로 내부 쌍으로 잰 것이다.
- **짧은 구간에서 오차가 크다.** 250m 미만 쌍의 중앙 오차율이 43.3%다.
- **추정값에는 방향 차이가 없다.** 원자료는 A→B와 B→A가 다르지만 추정식은 거리만 쓰므로 같은 값이 나온다.
- **원자료 값과 추정값이 섞인다.** 솔버가 과소 추정된 경로 간 구간을 골라 쓰면 이동시간이 실제보다 짧게 나올 수 있다. 결과에 추정 구간의 수와 시간을 따로 보고하는 것이 좋다.
- **그날 경로 전체가 아니다.** 학습 자료에 있는 56개 중 6개이고, 56개가 그날 DLA7의 전체 경로인지도 확인하지 못했다.
- **구역은 차량마다 완전히 갈려 있다.** 원래 배정에서 한 구역이 두 경로에 걸친 경우가 없다. 재배정 여지는 경로 경계 부근에 있다.
- **마감이 걸리는 물품이 적다.** 마감이 있는 물품은 166개(11.6%)다. 사전 조사에서 기록된 순서를 기존 평가 규칙으로 재생했을 때, 마감이 경로 종료 시각보다 이른 물품은 98개(6.9%), 지각한 배송지는 6곳이었다.
- **원자료에 자기 자신으로 가는 이동시간이 0이 아닌 지점이 1곳 있다.** `RouteID_a3f3caaa-7f27-4dc0-8f22-013269b2dff0:SD`의 값이 6.5초다. 고치지 않고 그대로 저장했고 `manifest.json`에 적었다.
- **부피는 상자 치수의 곱을 더한 값이다.** 실제 적재 가능 여부(모양, 쌓는 방식)는 반영하지 않는다.

## 팀원이 원자료를 직접 받는 방법

원자료는 용량이 커서(합계 약 2.3GB) 저장소에 올리지 않았다. `data/station_day/`만 쓸 거라면 받을 필요가 없다. 데이터를 다시 만들 때만 필요하다.

저장소 밖의 폴더에서 네 파일을 받는다.

```shell
curl -O https://amazon-last-mile-challenges.s3.us-west-2.amazonaws.com/almrrc2021/almrrc2021-data-training/model_build_inputs/route_data.json
curl -O https://amazon-last-mile-challenges.s3.us-west-2.amazonaws.com/almrrc2021/almrrc2021-data-training/model_build_inputs/package_data.json
curl -O https://amazon-last-mile-challenges.s3.us-west-2.amazonaws.com/almrrc2021/almrrc2021-data-training/model_build_inputs/travel_times.json
curl -O https://amazon-last-mile-challenges.s3.us-west-2.amazonaws.com/almrrc2021/almrrc2021-data-training/model_build_inputs/actual_sequences.json
```

| 파일 | 크기 |
|---|---:|
| `route_data.json` | 79MB |
| `package_data.json` | 375MB |
| `travel_times.json` | 1.82GB |
| `actual_sequences.json` | 9.7MB |

그다음 이 저장소 폴더에서 실행한다. Python 3.10 이상, 표준 라이브러리만 쓴다.

```shell
python data_fetch_station.py --raw 원자료를_받은_폴더
python dataset.py
```

같은 원자료로 실행하면 `manifest.json`의 `sha256`과 같은 파일이 나온다.
